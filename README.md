# CHW Companion

**An AI-assisted clinical triage tool for Community Health Workers (CHWs) in low-resource settings.**

Built for the Gemma 4 Good Hackathon (Kaggle × Google DeepMind, 2026). Apache 2.0.

---

## What it is

CHW Companion is a mobile-first web app that helps frontline health workers make a triage decision quickly when no doctor is in the room. The CHW types or pastes a symptom description in plain language — in any of the languages Gemma supports — and the app returns a structured assessment in two phases:

1. **Primary verdict** (≈3 seconds): urgency tier, urgency colour, recommended action, model confidence.
2. **Clinical detail** (streams in behind the verdict, ≈20 seconds): primary concern, warning signs to watch, questions to ask the caregiver, things not to do.

A **safety disclaimer is permanently visible** on every screen — this is decision support, not diagnosis.

A **triage queue** ranks each assessed patient by urgency so a worker juggling several cases can see who needs attention first.

A **cached-scenario layer** pre-generates responses for 20 canonical CHW presentations across 8 conditions (malaria, pneumonia, diarrhoea, malnutrition, obstetric emergencies, snake bite, meningitis, trauma) and 5 languages (English, Swahili, French, Hausa, plus an English fallback). When the input matches a cached scenario, the response returns instantly and works without a network connection. Novel cases fall back to live Gemma inference when connectivity is available.

## Who it's for

Community Health Workers in rural and underserved settings — about 1.5 million globally — who:

- See patients without a doctor on site
- Have intermittent or no internet connectivity
- Work in their local language, not always English
- Need a structured second opinion to back a referral decision

It is **not** a replacement for clinical training, a medical device, or a diagnosis tool. See `SAFETY.md` for the design rationale behind that boundary.

## How Gemma is used

The clinical reasoning is generated by an open Gemma model from Google DeepMind. Two complementary surfaces:

- **Live inference (production)**: Gemma 3 1B served from a Kaggle T4 GPU instance via a thin Flask wrapper. Two endpoints — `/triage/primary` (≈50 output tokens, ≈3.3 s warm) and `/triage/detail` (≈300 output tokens, ≈20 s warm). Both return validated JSON the frontend renders field-by-field. Multilingual: Gemma's native multilingual capability handles 35+ languages without a translation step.
- **Cached responses (offline path)**: pre-generated Gemma 3 1B outputs for canonical scenarios, bundled with the app as inline JSON. Sub-millisecond response time, works on `file://` with zero network calls. See `app/scenarios.json` for the 20 baked scenarios.

The honest division: **live inference for novel cases when online; cache for common presentations always**. The cache covers the cases CHWs encounter most; live inference covers the long tail when connectivity allows.

## How to run it

### Frontend only (no setup, no backend, runs anywhere)

```bash
# Open directly in any modern browser
chw-companion/app/index.html
```

Or serve over HTTP (recommended for a polished demo — some browsers add restrictions on `file://`):

```bash
python -m http.server 8765 --directory chw-companion/app
# Then open http://127.0.0.1:8765/
```

The frontend ships with the cached-scenario JSON inlined, so it works fully without a backend. Three sample-patient chips load canonical cases in one tap.

### With live Gemma inference

The backend is designed for Kaggle T4 (or any CUDA GPU host). Local CPU inference is too slow to be useful (~30–60 s per call) and the server falls back to mock mode when no GPU is detected.

```bash
pip install -r chw-companion/backend/requirements.txt
export HF_TOKEN=your_huggingface_token   # required to fetch Gemma weights
export CHW_MODEL_ID=google/gemma-3-1b-it # required: server.py defaults to gemma-4-e4b-it; production is 3-1b
python chw-companion/backend/server.py   # Flask on :5000
```

Endpoints:

```bash
curl http://localhost:5000/health
curl -X POST http://localhost:5000/triage/primary \
     -H 'Content-Type: application/json' \
     -d '{"symptoms":"4 year old, fever 39C, vomiting, malaria zone"}'
curl -X POST http://localhost:5000/triage/detail \
     -H 'Content-Type: application/json' \
     -d '{"symptoms":"4 year old, fever 39C, vomiting, malaria zone"}'
```

To force mock mode (useful for offline development): `export CHW_MOCK_ONLY=1`.

### Regenerating cached scenarios

The cache file `app/scenarios.json` is generated by a Kaggle notebook running Gemma 3 1B on T4 and then manually curated for clinical correctness. To regenerate:

1. Run `chw-cached-scenarios-generator-gemma-3-1b` notebook on Kaggle (T4 GPU, internet on, `HF_TOKEN` secret attached).
2. Download the populated `scenarios.json` from the notebook's output.
3. Spot-check each scenario manually: (a) `urgency` tier and `urgency_color` match the clinical severity (small Gemma models tend to collapse all responses to URGENT/red — the curation pass corrects this); (b) `language_detected` matches the input language (1B Gemma sometimes mistags Hausa as "Filipino" or similar); (c) every entry in `trigger_keywords` is literally substring-present in that scenario's `user_prompt`, and the keyword set is unique enough that it does not falsely match any sibling scenario's prompt.
4. Re-inline into `app/index.html` (the file:// path requires inline JSON, not a separate fetch).

## Hardware requirements

| Path | Hardware | Latency | Notes |
|------|----------|---------|-------|
| Cached scenarios | Any browser, any device | <1 ms | Works offline; covers 20 canonical presentations |
| Live primary phase | Kaggle T4 (or equivalent CUDA GPU) | ≈3.3 s warm | Gemma 3 1B fp16, ≈50 output tokens |
| Live detail phase | Kaggle T4 (or equivalent CUDA GPU) | ≈20 s warm | Gemma 3 1B fp16, ≈300 output tokens, streams |
| Local CPU (any) | Mock responses only | Instant (mock) | CPU inference of Gemma 3 1B is ≈70 s, unusable |

We do not claim CHW Companion runs on a $50 Android phone. Gemma 3 1B fp16 weights are ≈2 GB; running them at acceptable latency requires a GPU, not a low-end edge device. The production model is hosted on a shared inference tier (Kaggle T4); the app on the CHW's phone is a thin web client, with the cache layer providing offline coverage of the most common cases. This is the architecture that actually works under real bandwidth constraints — not the marketing version.

## Impact pathway

There are an estimated 1.5 million CHWs globally serving roughly 2 billion people who lack reliable access to clinical care. Most of them have a smartphone and intermittent connectivity. None of them have a clinical decision support tool designed for their specific context — local language, low literacy in clinical English, no specialist backup, a queue of patients who need triaging.

The path from this hackathon entry to that impact:

1. **Win or place** in the Gemma 4 Good Hackathon → visibility + small grant for next steps.
2. **Open-source the codebase** (Apache 2.0, already done) so any organisation can fork and adapt.
3. **Pilot with a CHW organisation** — partner with a single regional NGO or ministry-of-health programme to deploy in a defined catchment area. Validate triage agreement against trained nurses on the same cases.
4. **Clinical validation study** — measure CHW decision agreement, time-to-referral, and patient outcomes against a baseline-care arm. This is the bar required for WHO digital-health pre-qualification.
5. **Scale-up pathway** — WHO Digital Health Atlas listing, ministry-of-health endorsement in pilot countries, local-language scenario libraries for additional regions.

That is a multi-year arc. The hackathon entry is step zero — proof that the technical pieces fit together honestly.
